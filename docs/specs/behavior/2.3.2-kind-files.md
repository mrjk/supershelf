# 2.3.2 Kind files

Behavior. Index: [README](../README.md).

`scan vars` resolves variables in 2.3.1 and reads a kind file in 2.3.2. It does not write one. `scan feeds` creates, appends, rewrites, and drops rows. 3. File metadata is 2.3.3.

## Command

- supershelf scan feeds reads the kind file from 2.3.1 and may create, append, rewrite, or drop rows.
  scan files, scan match, and scan vars do not write kind files.
  scan vars reads when the mode reads.
- --kind-overrides-mode MODE sets the mode for this command.
  MODE is auto, manual, always, or disabled. The words are exact.
  A missing MODE, a different case, or any other value is a usage error.
  The flag belongs to scan feeds and to bare scan.
- SUPERSHELF_KIND_OVERRIDES_MODE accepts the same four words.
  Any other value is an error, including a different case and an empty value.
  Unset means omitted.
  The flag wins over the env var. The env var wins over config.kind_overrides_mode.
  Omitted everywhere means auto.
- --dry-run reads when the mode reads, and does not create, append, or rewrite.
  Log only when something would change.
  A file that would be created logs its path and its row count.
  A file that would gain rows logs its path and how many rows would be appended.
  A path change logs `path was "{old}", now "{new}"` for that digest.
  A replaced hash logs `hash was "{old}", now "{new}"` for that path.
  A row with an empty SHA whose path is not in this scan logs that it was not remapped and names the path.
  Several live files that share a digest log that digest and every path.
  Zero rows and no such change logs nothing. manual and disabled log nothing.
- Those path, hash, unmapped, and shared-digest lines are warnings.
  They are logged before the write. --dry-run logs them and writes nothing.
- Writes happen after the run succeeds. A var error writes nothing.
  There is no lock. Two overlapping runs can append the same path twice.
- scan feeds PATH matches only that file, so only that path can be fed or dropped.
  Other files of the same kind stay as they are. A PATH filter does not drop rows outside that selection.

## File

- The winning kind file is a list of rows. CSV, TOML, and YAML are the same list.
  One row is one file identity. A missing var is omitted.
  The examples are in [examples.md](../examples.md). .yml is the same text as .yaml.
- Files are UTF-8. Invalid UTF-8 is an error.
- .csv: one data row per file. The header is checked by name and case.
  A new file starts with SHA, then PATH. An existing file may start with PATH.
  When the first column is SHA, the second column is PATH.
  When the first column is PATH, SHA may sit anywhere after PATH.
  Other columns are the user's, in the user's order.
  An existing file is not reordered. Columns the user added stay.
  The app does not create a column for a var outside the schema, and it does not delete one.
  config.kind_overrides_sep is the separator. Omitted, it is a comma.
  The example profile sets ';'. YAML and TOML ignore it.
  The file is not scanned to guess the separator.
  Check the separator before the walk, at the same time as the date format.
  It must be a string of one character.
  A value that is not a string, an empty string, or more than one character is a config error.
  The message names kind_overrides_sep.
  Reject a letter, a digit, _, whitespace (including tab), ", ', /, \, or a newline.
  The message names the character and says to use a comma or a semicolon.
  Comma and semicolon are the expected values. | is allowed.
  Cells that contain the separator, a double quote, or a newline are quoted with ".
  The quote character stays ".
  Read and append use the configured separator.
  A file written with another separator fails the header check.
  That user error names the first column that was seen and mentions kind_overrides_sep.
  A leading BOM is accepted and left in place. It is not part of the first column name.
- .yaml and .yml: a bare list. There is no wrapping key.
  Each item has path, sha, and vars.
  sha is a sibling of path. It is not a key inside vars.
  Omitted sha, an empty sha, or a null sha is absent.
  vars is a mapping of var name to text. Omitted vars, or an empty mapping, adds no vars.
  Any other shape for vars is a config error. Unknown keys on the item are ignored.
- .toml cannot be a root list, so the file is [[rows]] tables.
  Each table has path, sha, and a [rows.vars] table. The items are the same as yaml.
- PATH in CSV, and path in TOML and YAML, is the path relative to the input, with / separators.
  It is an exact match, not a glob. Case is not folded.
  SHA in CSV, and sha in TOML and YAML, is the file sha256.
  A non-empty value is 64 lowercase hex digits. Anything else is a user error.
  The message names the kind file and the path.
  An empty SHA or sha is absent.
  In CSV, every column except PATH, SHA, and a feed column is a var name.
  In TOML and YAML, the names under vars are the var names, except a feed column.
  path, sha, and a vars mapping are unchanged. sha inside vars is a user var, not the identity.
  A TOML or YAML var name must match [A-Za-z_][A-Za-z0-9_]*.
  A CSV column other than PATH, SHA, and a feed column must be lowercase and match [a-z_][a-z0-9_]*.
  A non-empty CSV is checked before rows are applied. Any miss is a user error.
  The message names the file and what is wrong.
  The first column is SHA or PATH. path or Path says to use PATH.
  When the first column is SHA, the second column must be PATH.
  When the first column is PATH, SHA may sit anywhere after it.
  A missing PATH is an error.
  PATH in any later position is an error, except as the second column when the first column is SHA.
  A header named sha or Sha says the hash column is SHA.
  A column that is not lowercase, is not SHA, and is not a feed column names that column and says other columns must be lowercase.
  A duplicate CSV column, a duplicate name in one vars mapping, a missing path key in TOML or YAML,
  a bad name, or a namespace root is an error.
  An empty file, or a file of whitespace only, is an empty table, not a missing-header error.
  A blank line is skipped. A row with values and an empty PATH or path is an error.
  Two rows with the same path: warn, keep the first for a path lookup, leave the later row in the file.
  Two rows with the same non-empty SHA: error. The message names the kind file and both paths.
  Nothing is merged and nothing is written.
- A cell is one stored string. It is not a candidate list, and it is not compiled as Jinja,
  even when the text contains {{, {%, or {#.
  The rule layer has already stored its string, so the row does not change what that layer read.
  The kind file is the last assignment layer.
- An empty cell, a blank string, or a yaml or toml null is absent. The previous layer stays.
  This is not the template rule that an empty string is a success.
  There is no way to force an empty string over a previous value.
  A non-empty value is kept as text, including surrounding spaces, except a cell whose effective type is `date` below.
  A var value that is a number, boolean, date, list, or nested mapping is a config error. Quote scalars.
- A cell that sets an existing key keeps that key's first position and replaces the stored string.
  A new key is appended. CSV uses column order. TOML and YAML use key order inside vars.
- A row may set a feed column and names that do not start with `__`.
  A namespace root (`__file__`, `__match__`, `__profile__`, `__config__`, `__input__`) is an error.
  Any other name that starts with `__` and is not a feed column is an error.
  A key cannot contain a dot.

## Feed columns

- `scan feeds` writes these columns. 3.2.
  `scan vars` and `db import` ignore them.
  They are stored. They are not applied, not cast, and not a namespace error.
- The name is the var name with ASCII letters uppercased.
  `vendor` is `VENDOR`. `issued` is `ISSUED`.
  When that form is `PATH` or `SHA`, the column is `_PATH_` or `_SHA_`.
- A feed column matches `[A-Z_][A-Z0-9_]*`, contains at least one letter, and is not `PATH` or `SHA`.
  It is not a hash alias (`sha`, `Sha`).
  Those aliases stay the errors above. `SHA` is the identity column, not a feed column.
- Mixed case, such as `Vendor`, stays a CSV error.
- An all-uppercase name other than `PATH` and `SHA` is a feed column, so it cannot be a kind-file override.
- Identity updates must not edit a feed cell. `scan feeds` writes feed cells after those updates. 3.2.
  A schema-column rewrite keeps the column and its text.

## Date

- A non-empty kind-file cell whose effective type is `date` is parsed with the kind-file format.
  A text cell stays raw text, including a column named `date` when that name's type is `text`.
  `time` and `datetime` stay raw text here and are cast as those types.
- config.kind_overrides_date_format is an optional strptime format.
  When it is omitted, use config.default_date_format. That default is %Y-%m-%d.
  A blank or non-string value is a config error.
  The format must be valid for strptime and must include a year, a month, and a day.
  A time portion is allowed. Check that before the walk.
  One format applies to every date-typed cell in the profile.
- Strip the cell, then parse the whole string. Store year, month, and day as YYYY-MM-DD.
  Drop any parsed time. scan vars prints that stored value.
  A value that does not match stops the command.
  The message names the file, profile, input, path, the cell text, and the format that was required.
  There is no next candidate.
  A blank cell is absent. The previous layer stays, and the command does not stop.
- default_date_format still shows mtime and ctime in scan files, and it is this fallback.

## Load

- disabled does not render, open, create, append, or drop kind files.
  A listed path that exists is ignored. There is no per-file row. Import still runs.
- For each other mode, for each input and each rule kind that has a matched file, render the path list once.
  A kind with no matched file is never looked up, so always does not create a file for it.
  Cache that winner for the process by input index and kind.
  Cache the parsed rows by absolute path. Two inputs that resolve the same file share one table.
- The first existing file wins. Later hits are ignored, with no log.
  A path that exists and is not a file is an error. Do not try the next path.
  A symlink to a file is that file. Read and append follow it.
  A bad suffix, or any other content that does not parse, is an error.
  Do not try the next path, and do not append.
  An empty file, or a file of whitespace only, is an existing empty table.
- Create of a missing file is always only, and only when every candidate is missing.
  Create uses the first template only. Create missing parent directories.
  If a parent exists and is a file, that is an error and no kind file is written.
  auto appends only when a candidate exists. It does not create a missing file.
  manual reads a candidate when one exists. It does not create a file and does not add rows.
- The rule kind picks the file. `__match__.kind` does not change after matching, so the file and the row stay on that kind.
- The row identifier is the first step of `record_identity` for that matched file. 4.2.
  A bare `path` is path. A bare `hash` is hash. A list does not fall through inside the kind file.
  `[path, hash]` is path. `[hash, path]` is hash. `[path]` is path. `[hash]` is hash.
  Precedence is `SUPERSHELF_RECORD_IDENTITY`, then `config.record_identity`, then the match rule.
  The `--record-identity` flag does not change the kind-file key.
  `scan files`, `scan match`, and `inspect scan kinds` ignore it. A bad value does not stop those commands.
  `scan vars`, `scan feeds`, and `db import` read the first step. A bad value stops those commands.
  Path finds the row by the relative path. Hash finds the row by SHA. An empty SHA does not match a digest.
  Two inputs that share one kind file and the same identifier share one row.
  Put {{ __input__.path }} in the template when those inputs must not share rows.
- config.kind_overrides_mode is auto, manual, always, or disabled.
  Omitted means auto. Any other value is a config error. The words are exact.
  auto reads the winning file and may append, fill SHA, or rewrite PATH, as below.
  When no candidate exists, auto has no per-file row.
  manual reads the winning file and writes feed cells on rows that already exist. 3.2.
  It does not retarget, fill SHA, append, or drop rows.
  When no candidate exists, manual has no per-file row.
  always reads the winning file, or creates it, and applies the same writes as auto.
  Unmatched files have no kind, so they get no row. Files the walk skipped get no row.
  scan vars never writes a row.
  auto and always drop a row only under 3.3, after the path and hash updates below.
- auto and always must not drop a column or reorder rows.
  They must not clear or replace a lowercase var cell.
  Feed cells are written by scan feeds. 3.2.
  They may fill an empty SHA, replace a SHA after the warning below, and rewrite PATH after the warning below.
  When schema columns are missing from a CSV, append those names on the right.
  Pad each existing data row with empty cells. Leave a blank line blank.
  A file with no SHA column gets SHA inserted after PATH on the next successful auto or always write.
  Rows this run did not match keep an empty SHA. manual does not add or fill the column.
  An existing file that already has SHA is left in its column order.
- Path identity. Find the row by relative path.
  A missing path is appended. PATH and SHA are set. Other cells are empty.
  A row at that path refreshes SHA when the live digest differs.
  Filling an empty SHA is silent. Replacing a non-empty SHA warns first:
  `hash was "{old}", now "{new}"` for that path. Then the live digest is stored.
  A path-identity rename does not retarget. The old path stays until scan feeds drops it. 3.3.
- Hash identity. Find the row by SHA.
  Exactly one live file has that digest, and one row has it, and the path differs:
  warn `path was "{old}", now "{new}"` for that digest, then rewrite PATH. Cells stay on the row.
  No row has that digest, and a row at this path has an empty SHA: fill SHA on that row.
  Do not append a blank row over those cells.
  No row has that digest, and no row is at this path: append PATH and SHA. Other cells are empty.
  A row at this path whose SHA is a different non-empty digest is left as it is.
  Append the new digest as its own row. Warn that the path now has a new digest and the old row was kept.
  Any other row with an empty SHA whose path is not in this scan stays.
  One warning per such row says it was not remapped and names the path.
  Several live files of this kind share a digest: do not pick a path and do not append.
  A row that already has that digest keeps its PATH.
  One warning names the digest and every path.
- A hash retarget that would give two rows the same PATH stops the command and writes nothing.
  The message names the kind file, the digest, and both paths.
- A path already present is not appended again for path identity, including a duplicate row that was warned and kept as the first.
  Append in walk order, input index first.
  Do that once per absolute path, after the rows for this run have been read, and only if the run succeeds.
  A new row sets PATH and SHA in CSV, or path and sha in TOML and YAML.
  Other cells are empty, so a row created on this run does not change this run's values.
- When the only change is new rows and SHA is already a column, append at the end.
  A non-empty file whose last byte is not a newline gets a newline, then the new rows.
  When no schema column is added and no existing cell changes, earlier bytes stay.
  The new row bytes are one write at the end. A crash during that write can leave a partial last row.
  There is no temp file for that append.
  Inserting SHA, changing PATH, replacing SHA, or adding schema columns rewrites the whole file, including any new rows.
  The rewrite writes a temporary file in the same directory and replaces the kind file.
  A crash keeps the original. The text of each existing var cell and feed cell stays.
  CSV append uses the header after those columns are added, and config.kind_overrides_sep.
  PATH and SHA are filled. Other columns are empty.
- A new file is an always create, or an auto or always fill of an empty or whitespace-only file.
  manual leaves that file unchanged. Whitespace in a filled file is not kept.
  A new CSV header starts with SHA, then PATH.
  Uppercase feed columns follow, in schema dictionary order, then the lowercase schema names in that same order.
  Schema dictionary order is the key order of kind_schema.vars_schema when the kind is listed.
  Otherwise it is the declared vars_schema order.
  Uppercase columns are added only when feeds is a non-empty list.
  Only those names are uppercased, and the feeds list does not reorder them.
  A feed name that is not a schema column follows those, in feeds list order.
  Omitted feeds, or an empty feeds list, adds no uppercase columns.
  path and sha become _PATH_ and _SHA_.
  A kind_schema entry supplies its local names. Otherwise declared vars_schema names are used.
  A name that starts with `__` is left out.
  A schema name that is not a legal lowercase column is left out of that group.
  Its uppercase feed column is still written when that form is a legal feed column.
  The app does not add a lowercase column for a var outside the schema.
  This order is only for a file this run creates. An existing file keeps its column order.
  With no schema columns, the header is SHA and PATH.
  Omitted, that header is SHA,PATH. The example semicolon with no schema writes SHA;PATH.
  The header line has no data.
  Then one row per matched file. Each new row sets PATH and SHA and leaves the other cells empty.
  A new TOML or YAML file is the same rows, with path and sha set and vars omitted.
  Several live files that share a digest and whose first step is hash produce one warning and no row for that digest.
- An empty kind_overrides_config creates and appends nothing in every mode.
  In every mode except disabled, -vv still logs that there is no candidate list.
  Omitted uses the default list from 2.3.1.
