# 2.1 Scan files

Behavior. Index: [README](../README.md).

`supershelf scan` runs files, kinds, vars, and feeds, in that order. Each step can be run alone. It does not write the sqlite file. `db import` does. 4.

`supershelf scan` and `db import` share one PATH-scoped kept list. The list keeps every kept file. A step prints its own rows and leaves the list intact. `scan files` stores identity on that list. `scan match` reads the whole list. `scan vars` lists variables for the files those earlier steps would print, not for every matched file. 2.3.1. A step run alone builds the list itself. `PATH` is fixed for the run. A list passed in from an earlier step is not walked again. The stages are 2.1.3.

Kind-file updates are computed on that run before any kind file is written. A resolve error writes no kind file. `db import` writes documents from the import comparison in 2.1.3, not from the identity statuses.

`--dry-run` prints the same plan and writes nothing. It does not create the sqlite file, the cache file, or a kind file.

Comparison is against the document sqlite file. A missing or empty file means every live matched file is a change. The file stays missing until `db import` writes a row.

`scan` and each step print the rows that differ. A `missing` document is printed only when `db import` would append that event. `inspect scan` prints the full set, including unchanged rows. 6.

A kept file that no rule claims is listed by `scan match` on every run. 2.2.

`PATH` is the relative path from the walk. The same path in two inputs is two rows. There is no second selector.

One profile can commit before a later profile fails. Profiles do not share rows.

Stdout columns for `scan feeds` start with the fields that step already has, in this order: profile, input, sha, path, status. profile is included only when more than one profile is selected. A field that step does not already have is left out. Other columns follow that prefix and keep their order. `inspect scan feeds` uses the same columns. 6.

`scan files`, `scan match`, and `scan vars` print a default subset. Each step names that subset. profile is the first of those columns when more than one profile is selected. It is left out of the row when one profile is selected. The other fields stay on the row. `--columns` selects them. The table, json, yaml, and csv use that subset. `inspect scan files` and `inspect scan vars` use the same columns. `supershelf scan` prints one section per step. The files, kinds, and vars sections use that step's default columns. 6.

## 2.1.1 Command

- supershelf scan files [PATH]: file-identity changes against the document sqlite file.
- Status for this step is `new`, `generation`, `move`, `missing`, `refresh`, or `duplicate`. Kind and var changes are later steps. The words are behavior 4.
- The comparison is 2.1.3. It uses the matched rule's `record_identity`. 4.2. Kind, rule, and variable differences stay off this status. An mtime, ctime, or input-index change is still `refresh` when the stored kind, rule, or variables differ. `db import` prints `vars` for that same file. 4.
- Prints rows this run would write. `inspect scan files` prints every kept file, including `unchanged`.
- There is no `--quick`. The diff reads mtime, ctime, and sha256.
- Opens an existing sqlite file read-only. It does not create the database file or the cache file.
- Default columns: input, path, status, mtime, ctime, sha256.
  profile is the first column when more than one profile is selected.
  sha256 is the lowercase hex digest. The header is sha256.
  input is the 1-based index in that profile's inputs list, not the directory path.
  path is relative to the input directory.
  mtime and ctime are the stored UTC times shown with config.default_date_format.
- A `PATH` that matches no kept file and no in-scope document is an error.

## 2.1.2 Walk

- Each selected profile is scanned on its own. Profiles do not share results.
- scan files only prints. It does not create the database file or the cache file. It reads sha256, mtime, and ctime for every kept file.
- For each input, get the path value, and template render it.
- If that path is relative, resolve it from `__config__.root_dir`. Relative input paths are resolved when the input is processed.
- The input path must be a valid path. If it exists and is not a directory, that is an error.
- If the input directory is missing, log a warning and skip that input.
- Get parameters depth, include, exclude, and follow_symlinks.
- depth: 0 means no recursion limit. 1 means only the input directory. 2 means that directory and one subdirectory level. 3 adds the next level, and so on.
- Omitted depth means 0. Negative depth is an error.
- follow_symlinks is an input option. Default true. False skips symlinks.
- A followed symlink is stored as the path under the input. A symlink cycle logs a warning and that path is skipped.
- Globs match the path relative to the input directory. * stays in one directory. ** crosses directories.
- If include is set, keep files that match at least one include pattern. If include is omitted, start from every file the walk found.
- If exclude is set, drop matching files from that set. If exclude is omitted, drop nothing.
- Empty files are ignored.
- An unreadable file logs a warning and is skipped.
- An unreadable directory logs a warning and is not descended.
- Do the filesystem walk
- store results in a InputScanResult:
  - config: hold the input config
  - index: 1-based position in that profile's inputs list. A skipped input keeps its position.
  - results: hold a list of InputFile objects
- Get file metadata:
  - mtime is filesystem st_mtime. ctime is filesystem st_ctime. Stored as UTC ISO-8601 with a numeric offset, so datetime.fromisoformat can parse them. Example: 2026-10-29T16:28:00+00:00. Include fractional seconds when the filesystem value has them.
  - sha256 is the lowercase hex digest of the file contents.
  - InputFile expose all Path primitives (parent, stem, ext, etc ...)

## 2.1.3 Run

One run per profile. Profiles do not share the run.

The run holds every kept file, and the documents the identity comparison adds for paths that are no longer kept. Those added rows are `missing`. A step does not drop a kept file because that step would not print it. `inspect scan` prints the same run with unchanged rows included. 6.

`PATH`, `--dry-run`, and `--kind-overrides-mode` are fixed for the run. A different value is a different run. There is no kind selector.

- Walk. 2.1.2. Empty files are already gone. `scan match` does not read mtime, ctime, or sha256. `scan files`, `scan vars`, `scan feeds`, and `db import` read them on that same kept set. A file that cannot be read then leaves the kept set. A document at that path is `missing` when identity runs.
- Match. 2.2. Kind, rule, and groups. This stage does not decide an identity status.
- Identity. After match, and after sha256 is read. This is what `scan files` prints. It does not read kind files. It compares path, hash, and clocks, using the matched rule's `record_identity`. 4.2. For a path that already has a document, the stored kind, rule, and variables are what this comparison sees, so a kind-only or variable-only change is not an identity status.
- Vars. 2.3.1. After match. It does not need the identity statuses. It reads kind files.
- Import comparison. After vars. This is what `db import` prints. It uses the resolved kind, rule, and variables. It does not reuse the identity statuses. A generation or a move carries the new variables in that one event and is not also `vars`.
- `scan feeds` writes after vars. 3. `db import` writes after the import comparison. 4.

`scan match` is the walk plus match. `scan files` is the walk, match, the hash, and identity. `scan vars` is the walk, match, the hash, and vars. `db import` is the walk, match, the hash, vars, and the import comparison.

When the clock and the variables both change, `scan files` prints `refresh` and `db import` prints `vars`.
